# ENV-004 — Prepared-Range Proactive Reclaim Probe

> **Status:** FROZEN CAPABILITY CONTRACT

## Bounce question

Can a range that already has anonymous swap backing be preferentially moved out of RAM by cgroup v2 proactive reclaim while an equal matched control range remains substantially resident?

This is a research-instrument calibration experiment.

It is **not** a memory-policy experiment.

## Pseudo-Council convergence

### Kernel / VM reviewer

Use the existing successful low-pressure `MADV_PAGEOUT` preparation step, then invoke cgroup v2 `memory.reclaim`.

Use:

    16M swappiness=max

so the proactive reclaim request targets anonymous memory.

The cgroup interface can over- or under-reclaim; the observed effect must therefore be measured rather than assumed.

### Measurement reviewer

Use two equal anonymous mappings:

- target: 16 MiB;
- control: 16 MiB.

Touch both fully.

Only the target receives `MADV_PAGEOUT`.

Measure `mincore(2)` residency:

1. before pageout;
2. after pageout;
3. after proactive reclaim;
4. after retouch.

Also record swap, reclaim counters, call duration, return status, and deterministic content integrity.

### Experimental reviewer

Balance target identity A/B across four independent hosted-runner blocks so mapping identity is not silently confounded with the intervention.

Keep the cgroup away from `memory.high` pressure:

    MemoryHigh = 256 MiB
    MemoryMax  = 320 MiB

The two 16 MiB mappings plus process overhead are intentionally far below the high boundary.

### Falsification reviewer

The instrument is not selective enough if proactive reclaim removes target and control residency to a similar degree.

A successful syscall alone is not capability evidence.

### Authority reviewer

Even an effective ENV-004 result would authorize only a later matched causal intervention.

It would not establish a Linux defect, a beneficial application hint, or a need for a coordination plane.

## Capability classification

Each trial reports continuous measurements.

The aggregate Council may classify the instrument as:

- **SELECTIVE** — target residency is strongly reduced while control residency remains high and contents are intact;
- **NONSELECTIVE** — both mappings lose substantial residency;
- **INEFFECTIVE** — target remains substantially resident;
- **UNAVAILABLE** — required kernel interface cannot be invoked.

For the initial machine check, the following operational thresholds are pre-registered:

    target resident fraction after reclaim <= 0.50
    control resident fraction after reclaim >= 0.90
    content integrity = true

These thresholds define instrument usability only; they are not scientific claims.

## Kernel-interface note

Linux documents `memory.reclaim` as proactive reclaim of a target cgroup. The request may over- or under-reclaim, and `swappiness=max` requests anonymous-only reclaim.

That makes direct measurement essential.
