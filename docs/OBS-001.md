# OBS-001 — Dual-Sided Memory Observation Baseline

> **Status:** CONTRACT DRAFT / BLOCKED ON ENV-001 CHARACTERIZATION

## Question

Can application-side demand transitions and OS-side memory behavior be placed on one sufficiently precise timeline to identify the sequence that precedes performance degradation?

## Observation model

### Application demand events

Minimum intended fields:

- monotonic timestamp;
- workload/process identity;
- phase/state;
- allocation or working-set change where controlled;
- operation start/end;
- operation latency.

Controlled workloads may additionally expose future-access truth for later validation.

### OS memory events

Candidate fields, conditional on ENV-001:

- memory usage;
- anonymous/file-backed breakdown where available;
- PSI memory pressure;
- faults and major faults;
- refault counters;
- scan/steal/reclaim counters;
- swap activity;
- cgroup memory events/statistics.

### Outcome events

- workload throughput or completion time;
- latency distribution;
- stalls or timeouts.

## Core requirement

All event streams must share a monotonic or explicitly aligned time basis.

A correlation without time alignment is not sufficient.

## First goal

OBS-001 is not an optimization experiment.

It should produce a synchronized event stream from a controlled workload and the OS observation surface selected after ENV-001.

## Exit condition

OBS-001 exits when the repository can reproducibly answer:

> What application transition occurred, what OS memory transition followed or coincided with it, and what user-visible consequence was measured?

No coordination policy is required for OBS-001.
