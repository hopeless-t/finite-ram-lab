# ENV-002 — Isolated Memory-Control Capability Probe

> **Status:** IMPLEMENTED / INITIAL CONTRACT

## Question

Can a GitHub-hosted Ubuntu runner place an isolated child workload under an explicit cgroup v2 memory budget and expose the resulting limits/usage back to the workload?

## Why this exists

ENV-001 established that useful memory telemetry is visible.

OBS-001 needs a repeatable way to create controlled memory pressure without stressing or reconfiguring the entire runner.

ENV-002 therefore tests **isolated controllability**, not memory-policy quality.

## Method

The workflow starts a transient systemd unit with:

- `MemoryHigh = 192 MiB`;
- `MemoryMax = 256 MiB`;
- a bounded 64 MiB touched allocation.

The child process records its own cgroup path and memory controller state before and after allocation.

## Acceptance

ENV-002 PASS requires:

1. the child process is placed in a cgroup v2 path;
2. `memory.current` is readable;
3. `memory.high` equals the declared 192 MiB budget;
4. `memory.max` equals the declared 256 MiB budget;
5. touched allocation increases observed cgroup memory usage;
6. no OOM event is observed.

## Safety boundary

ENV-002 does **not** intentionally approach `memory.max`.

It verifies that a bounded control surface exists before later pressure experiments use stronger loads.

## Non-claims

ENV-002 does not establish:

- reclaim quality;
- Linux page-replacement quality;
- application/OS coordination benefit;
- bare-metal memory behavior.

A PASS only authorizes controlled hosted-runner pressure experiments.
