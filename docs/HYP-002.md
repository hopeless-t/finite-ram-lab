# HYP-002 — Randomized Recency vs Future Semantic Need

> **Status:** FROZEN CONTRACT / NOT YET RUN

## Question

Under 160–162 MiB memcg pressure, does randomized pre-burst access recency determine which of two matched anonymous regions retains residency, independently of which region the application will need next?

## Factorial design

Each of 16 independent runner blocks executes all eight cells:

```text
MemoryHigh:
160 / 162 MiB

recent_identity:
A / B

future HOT identity:
A / B
```

Total:

```text
16 blocks x 8 cells = 128 trials
```

## Matched regions

Two anonymous private mappings:

```text
A = 32 MiB
B = 32 MiB
```

Both mappings are fully faulted in.

Before the burst, both receive the same number of explicit touches.

The order is controlled:

```text
older region
then
recent region
```

with two complete touch rounds for each.

Thus touch count is matched while final ordering is randomized.

## Future semantic identity

`hot_identity` is randomized independently of `recent_identity`.

Therefore:

```text
HOT == recent  -> semantic demand aligns with recency cue
HOT == older   -> semantic demand conflicts with recency cue
```

The kernel receives no semantic hint.

## Pressure workload

After recency preparation:

- allocate/touch 96 MiB burst;
- capture A/B residency with `mincore(2)`;
- retouch the declared HOT region;
- record latency and OS counters.

MemoryMax remains 320 MiB.

## Primary outcome

For each trial immediately before HOT reuse:

```text
recent_fraction - older_fraction
```

For each runner block average the eight trial contrasts.

Primary directional hypothesis:

```text
mean block contrast > 0
```

Inference:

- exact one-sided sign-flip over all 65,536 block sign assignments;
- 20,000-resample runner-cluster bootstrap interval for the mean contrast.

## Key secondary outcome

Within each runner block compare:

```text
mean(log HOT-retouch latency | HOT == older)
-
mean(log HOT-retouch latency | HOT == recent)
```

Positive values mean conflict between future semantics and the recency cue is costly.

Report exact sign-flip inference and a cluster-bootstrap ratio.

This is secondary; it cannot rescue a negative primary recency-selection result.

## Mapping-identity falsification

Report primary residency contrasts separately when:

```text
recent = A
recent = B
```

A result that appears only for one mapping identity would weaken the recency interpretation.

## No intervention

HYP-002 uses no:

- MADV_PAGEOUT;
- MADV_COLD;
- proactive reclaim;
- mlock;
- coordinator;
- kernel modification.

## Scientific meaning

A positive primary result would establish that controlled past recency/order affects residency selection under the declared pressure workload.

If the key secondary result is also positive while HOT identity is independently randomized, the experiment would directly expose a bounded mismatch between:

```text
OS-visible past-use cue
and
application-known future-use need
```

It would still not establish that a particular hint or coordination mechanism can exploit that information safely.

## Authority boundary

HYP-002 is a bounded hosted memcg experiment, not a general claim about Linux reclaim policy.
